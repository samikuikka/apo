**From invitation to recorded evidence.** You were invited to an apo installation that someone else operates. You never self-host anything, you never touch their data, and your agent runs on *your* machine, apo only records what happened and why it passed or failed.

:::note
This page begins after you receive an invitation link. Don't have one? Accounts on a hosted apo are invitation-only by design, ask the installation's administrator. If you're the one operating the server, start with the [Quickstart](/quickstart/) instead.
:::

## 1. Accept the invitation

Open the link you were given. It takes you to the installation's `/join` page:

```text
Create your apo Project

Name            [ Ada Lovelace ]
Email           ada@example.com        (locked to the invitation)
Password        [ •••••••• ]
Project name    [ My evaluations ]

           [ Create account and Project ]
```

Submitting creates **your own Project**: a private workspace for your tasks, runs, and evaluations. You are its only owner. The person who invited you cannot see inside it, and you cannot see theirs. Acceptance is one atomic action: it either fully works or nothing was created.

## 2. Install the CLI

```bash
npm install -g @apo-ai/cli
```

Node.js 20 or newer (the CLI package's `engines` floor). The CLI is the only thing that runs your agent, the hosted server never executes your code.

## 3. Connect this Project

Your Project's Tasks page shows an exact login command, copy it from there, because it already contains the installation's real URL and your exact Project ID:

```bash
apo login --backend https://your-apo.example --project abc123def456
```

```text
Email: ada@example.com
Password: ********
✓ Logged in as ada@example.com
  Backend:  https://your-apo.example
  Project:  My evaluations (abc123def456)
  Key:      apo_key_9f2c... (full)
  Saved to: ~/.apo/credentials
```

The CLI stores a Project-scoped API key on your machine (`~/.apo/credentials`). It is never displayed in the browser, and it grants access to exactly this one Project.

## 4. Choose a Task source

Two supported paths, same destination, one recorded run:

| Path | Use it when |
|---|---|
| **Your own repository**: install `@apo-ai/sdk`, define a Task (`<task-id>.eval.ts`) next to the code it evaluates | You have an agent and want evaluation in your repo. See [Define a Task](/guides/define-a-task/). |
| **The maintained example**: a ready task tree with fixtures | You want to see a full recorded run before wiring your own agent. See [START-HERE.md](https://github.com/samikuikka/apo/tree/main/apps/example-service/e2e/agent-task-demo). |

Your model-provider credentials stay on your machine either way. Publishing a Task sends metadata (name, adapter, checks) never your source code, fixtures, or secrets.

## 5. Publish and run

Publish makes your Task catalog visible to the dashboard; run executes it locally and records the verdict:

```bash
apo task publish --dir ./tasks
# ✓ Published 3 tasks to abc123def456

apo task run my-task --dir ./tasks
```

```text
Executor: caller (recorded in abc123def456)
Revision: clean worktree 9f2c7d81e4b90f6a2c3d4e5 from github.com/your-org/your-agent

PASS my-task
  Checks:
    PASS used-source-document
    PASS parties-are-complete

Run:     run_9f2c7d81e4b90f6a2c3d4e5f6a7b8c9d
Inspect: apo runs show run_9f2c7d81e4b90f6a2c3d4e5f6a7b8c9d
```

:::tip
A **FAIL is a successful onboarding.** apo recorded a trustworthy verdict and the evidence to debug it. The only bad outcome is no recorded run at all.
:::

The `Run:` line is the run's exact identity, every later command takes it. For the full record (status, cost, tokens, trace, deliverables), run the printed `Inspect:` command; when the command finishes, open **Runs** in the dashboard for the verdict, per-check breakdown, trace, and deliverables, all pinned to the same run ID.

## What you got

- A private Project, owned by you, on shared infrastructure
- Binary verdicts with explained failures for every run
- Traces and deliverables recorded automatically
- Zero servers to operate
