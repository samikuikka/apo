A test is one assertion about a run. You write it with the `test(...)` function returned by `task()`, and a task usually needs several: not one vague judgment, not one brittle exact-match. Every test records into the same breakdown.

For *why* code assertions and LLM judges are the same kind of thing, see [Why apo](/why-apo/). This page covers what a test looks like and how to read what comes back.

## Two kinds, one shape

Every test asserts one of two things: **what the agent did** (did it call the right tool? did anything error?), or **what it produced** (is the output correct?). Both are written the same way, and both report into the same breakdown.

A test about what the agent did reads the run's trace. It's fast, deterministic, and free:

```typescript
test("used-source-document", (t) => {
  t.calledTool("read_file", { input: { path: "contract.pdf" } });
  t.noFailedActions();
});
```

A test about what the agent produced reads the deliverables your adapter collected. It can check a value against a schema, or hand the value to an LLM and ask whether it's actually good:

```typescript
test("parties-are-complete", async (t, { deliverables }) => {
  t.check(deliverables.parties, matches(partiesSchema));
  await t.judge(
    deliverables.parties,
    "PASS when every named party is captured without false positives.",
  );
});
```

The `t` object carries assertions like `calledTool`, `noFailedActions`, and `check`. The second argument to the callback is a context with `{ deliverables, files, task }`: `deliverables` is the task-selected subset of what your adapter returned, inferred automatically; `files` is the task's inputs. The full method list lives in the [Assertions API](/reference/assertions/).

## How the result is computed

If every test passes, the run passes. If any test fails, the run fails. No weighting, no scores, no partial credit.

A test never throws. It records. One test can make several assertions, and you'll see each in the breakdown. A failing assertion doesn't stop the test; it keeps going and reports everything it found.

That pass/fail only exists when the execution itself was sound. When it wasn't, apo records an error instead of a verdict, see [Verdict validity](#verdict-validity).

## Verdict validity

A PASS/FAIL verdict claims "the agent ran, and here is what it produced." When the model backend itself failed (rate limits, outages, bad credentials) that claim would be a lie. So apo watches the run's generations, and when **most of them ended in error**, it records **no verdict**:

- The run lands with status `error` and no PASS/FAIL, the dashboard shows **no verdict**, and the CLI shows `Result: -` with a `Generations: 17/22 errored` line.
- The tests are still computed and stored, as **diagnostic evidence**, not as a control signal. A "PASS" over a run where 17 of 22 model calls died says nothing about your prompt.
- Cost and token totals are marked **partial**: errored generations are excluded (a failed provider call often reports no usage at all, which would otherwise project as a suspiciously cheap run), and unpriced calls are excluded from cost the same way.

A minority of errored generations (the run recovered) keeps its normal PASS/FAIL verdict; the totals are still disclosed as partial. The strict rule is: silence beats a wrong signal.

The same rule applies one level down, per check. When an LLM judge never answers — unreachable endpoint, HTTP error, empty or truncated reply after its one retry — the check records `outcome: "error"` (`pass: false`) instead of pretending the judge said FAIL. The dashboard badges it **No verdict** (warning, not red), the run's checks line counts it as `N no verdict` apart from failures, and rejudge stability skips the sample rather than reading it as a flaky fail. A missing judge configuration records the same `outcome: "error"`.

A check's outcome rolls up from its failing assertions: it is `error` only when every failing assertion lacks a verdict and at least one of them is a judge error; one genuinely failing assertion makes the whole check a FAIL. So a check whose failures are a judge error plus an `unsupported` assertion (missing trace evidence) is `error`, while a check that fails *only* on `unsupported` assertions is `unsupported` and fails the run.

At run level, when checks with outcome `error` are the **only** non-passing checks, nothing was judged a failure and not everything was judged, so the run records **no verdict** too: status `error`, no PASS/FAIL, and a message that names the cause (`No verdict: 1 of 12 checks got no verdict from the judge (judge error or no judge configured); the other 11 passed.`). `apo task run` prints `NO VERDICT` and exits `2`. Any genuine or `unsupported` failure beside it keeps the run a FAIL. The run records why it has no verdict in `no_verdict_reason` (`judge`, `generations` for the rule above, `executor` when the execution itself failed); the CLI, SDK and dashboard read that field, and the message is for people. Only against a backend that predates the field do they fall back: `apo runs correct` reads a null `run_pass_result` as no verdict, and the other surfaces (`apo task run` included) read the message's `No verdict: ` prefix.

Such a run is still re-judgeable (`apo runs rejudge` records a separate judgment; the run keeps its own verdict) and correctable (`apo runs correct`): a correction on the errored check supplies the missing verdict and the run becomes PASS or FAIL.

## The second judge

One judge gives you a verdict. Two judges of different kinds give you an error bar. apo can grade every `t.judge` call twice: your normal LLM judge decides the verdict, and a **second judge** — a typed-decision model that cannot generate text — grades the same deliverable alongside it and reports its verdict as a probability and a confidence. It never changes the verdict; it tells you how much to trust it.

```bash
export APO_SECOND_JUDGE_MODEL=typesafe/jev-1.13
```

The second judge needs a decisions endpoint (OpenRouter-style `/alpha/decisions`). When your primary judge talks to OpenRouter directly, that's automatic. When it's routed through a proxy (LiteLLM, a gateway, a direct provider), give the second judge its own connection — it cannot ride a chat proxy:

```bash
export APO_SECOND_JUDGE_BASE_URL=https://openrouter.ai/api/v1
export APO_SECOND_JUDGE_API_KEY=sk-or-...
```

Each decisions endpoint speaks its own request/response dialect, so the second judge has a provider switch: `APO_SECOND_JUDGE_PROVIDER` selects one explicitly, and unset it auto-detects from the base URL — an `api.openai.com` host selects the OpenAI Decisions dialect, anything else the OpenRouter dialect. The OpenAI dialect is reserved until the endpoint's schema is public: selecting it records a clear `error` on the evidence (and never sends a request) rather than guessing a request shape. Adding any other decisions provider is one provider object in the SDK's `second-judge.ts` — the knob, evidence contract, and wiring stay identical.

Why a *non-generative* second opinion: text judges sometimes fabricate evidence in their reasoning — quoting findings that aren't in the deliverable — and then verdict off their own fabrication. A decision model can't write a quote, so it can't do that. Measured against production data (2,094 judged checks re-played through the second judge): 96% agreement, and the disagreements clustered exactly where judges contradicted rubric text or rubrics couldn't decide the case.

The marks state **measurements, not diagnoses** — they never claim *why* the judges differ, only that they did, and how confident the second one was:

| Mark | Meaning |
|---|---|
| *(nothing)* | Both judges agree with confidence — the check is corroborated |
| `✓✗ 0.99` | The judges' verdicts differ; 0.99 is the second judge's confidence |
| `✓✓ ·0.31` | They agree, but the second judge was low-confidence — weak corroboration |
| `2nd ✕` | The second opinion failed to arrive (transport error, not a verdict) |
| `2nd ⊘` | No second opinion was possible: the value exceeded the second judge's context limit — not an outage |

In the CLI they sit at the end of the check line, with one sentence under contested checks, and one fact line after the checks:

```
  Checks:
    PASS c-001 — Accept independent-development carve-out
    PASS c-003 — Restore 'publicly available' exception ✓✗ 0.99
      Verdicts differ — second judge contradicts at 0.99 confidence.
    FAIL c-005 — Term of agreement survives for trade secrets ✓✓ ·0.31
      Second judge unsure (0.31) — weak corroboration.

  Second judge: 12 corroborated · judges split on 1 · 1 unsure
```

### When the value is too large for the second judge

A deliverable can fit the primary judge's context and not the second judge's — a full redlined document with tracked changes, margin comments, and the complete marked-up text is hundreds of KB. The provider rejects the state before judging, and apo records it as a skip (`2nd ⊘`, `skipped` on the evidence, counted in the run's fact line as `N skipped (value too large)`) — an honest "no second opinion for this check", never "failed to arrive", so an oversized deliverable can't masquerade as an outage.

When the check only needs part of the value, give the second judge that part: `opts.secondJudgeValue` grades a smaller view with the second judge only, while the primary judge still sees the full value — so other criteria that need the complete document (e.g. "terms the counterparty never touched must survive") are unaffected.

```typescript title="my-task.eval.ts"
test("sla-credit-cap-redlined", async (t, { deliverables }) => {
  await t.judge(
    deliverables.redlinedDocument,
    "PASS when the SLA credit cap is marked up from 15% to 30%.",
    {
      // The tracked-changes section answers this criterion; the second
      // judge can't read the whole 351 KB document.
      secondJudgeValue: deliverables.redlinedDocument.trackedChanges,
    },
  );
});
```

The evidence records `projected: true` when the second judge graded a projection — its verdict corroborates the projection, not the whole deliverable, and the dashboard says so.

Agents reading `--json` get the raw evidence instead of marks: every check carries `judge.secondJudge` with `choice`, `passProbability`, and `confidence` — branch on the numbers, not on ANSI.

:::note
Everything works without the second judge. Unset, `APO_SECOND_JUDGE_MODEL` changes nothing: no marks, no lines, output byte-identical. Code-assertion and agentic (`t.agent`) tests never get a second judge — only `t.judge` calls do.
:::

### Cascade mode

The second judge can do more than corroborate: in **cascade mode** it answers first, and a verdict at ≥ 0.95 confidence stands without calling the primary judge — a measured ~70% cut to judging spend with ~0.5% of verdicts differing. The economics, the failure boundary, and the routing rule that decides which judge a test needs live on the [Judging page](/concepts/judging/).

## The agentic judge

`t.judge` hands the judge a value. `t.agent` hands it a question. The agentic judge is a tool-using LLM session that investigates the run's own evidence — the deliverables, the trace, this task's prior runs — and only then verdicts. Where `t.judge` asks "is this value good?", `t.agent` asks "go find out whether the run holds up."

```typescript title="extract-parties.eval.ts"
test("summary-grounded-in-invoice", async (t) => {
  await t.agent(
    "PASS if every line item, seller, and amount the summary claims is consistent with the extracted result. " +
    "Investigate the deliverables before deciding. FAIL if the summary asserts anything the extracted " +
    "data contradicts or cannot support.",
  );
});
```

Some criteria can't be answered from a pre-extracted slice. Groundedness across a long document, cross-references between deliverables, "did the agent actually read what it claims to have read" — the evidence for the verdict is scattered, and pulling it into the check means writing extraction code that duplicates the judgment. `t.agent` lets the judge gather its own evidence with read-only tools — read and regex-search the deliverables, query the run's trace, list and inspect this task's prior runs (human corrections included, frozen once per evaluation), read the task definition — and end the session with `finish_verdict`, whose reasoning must cite the evidence it relied on. The exact tool surface and options live in the [Assertions API](/reference/assertions/).

The session is bounded and honest by construction:

| Guarantee | How |
|---|---|
| **Bounded** | A hard budget of turns, tool calls, wall-clock time, and bytes read (defaults in the reference). When one runs out, every tool starts answering "call finish_verdict now" |
| **Fail-closed** | A session that ends without a verdict records a **failure** with the explanation — never a silent pass |
| **Recorded** | The whole session lands in the check report (`evaluator_type: "agent"`): the transcript as a content-hashed manifest of what was actually read, plus the verdict's reasoning |
| **Stateless** | Each check gets a fresh session; no remembered judgment leaks between checks (remembered judgments were shown to cascade errors) |
| **Traced** | The investigation is itself an `AGENT` span in the run's trace, with the verdict summarized |

A budget-exhausted failure looks like this:

```text
    FAIL summary-grounded-in-invoice
      agentic judge session ended without a verdict (budget exhausted after 12 steps; last tool: search_deliverable)
```

That failure is a signal about your budget or instruction, not about the agent — raise `budget`, tighten the instruction, or drop back to `t.judge` with a pre-extracted value.

An agentic session costs real money and runs minutes, not seconds. Reserve it for the criteria that genuinely need investigation and keep the rest on `t.check` / `t.judge`. The judge model must be tool-calling capable (same judge config chain as `t.judge`, overridable per call), and the [second judge](#the-second-judge) never applies — only `t.judge` calls get one.

## Re-judging a run

A verdict is only meaningful together with the conditions that produced it: the task definition it ran under, and (for judged tests) the judge model that was configured. Change the judge and the *same deliverables* score differently: on rubric-heavy tasks, roughly one in six judged criteria flips with the judge, not the agent. That variance is a property of your eval, and you should be able to see it without re-running the agent.

`apo runs rejudge` replays a completed run's tests against the deliverables the run already stored, under a judge you choose now. Each replay is recorded as a **judgment** on the run:

- The run's original verdict stays first and canonical, `runs show`, the dashboard, and comparisons keep reading it. Judgments accumulate next to it, never over it.
- Replay scores against the run's **pinned task definition revision** (the exact `*.eval.ts` that ran) so a re-judged score answers "same eval, different judge?". Scoring old deliverables against a *new* rubric is a different question and is stamped as such.
- The full test set replays every time. Re-judging only the criteria that failed would keep the draws you like and discard the rest, a ratchet toward PASS that destroys exactly the variance you're measuring.
- Replay refuses runs whose deliverables are incomplete, for the same reason verdict validity suppresses errored runs: a missing deliverable must not dress up as a low score.

Judging the same run several times (`--samples`) turns "this test failed" into "this test fails 2 of 5 times", which is what you actually need to know before spending agent budget chasing it.

:::tip
Before changing your task's judge model, re-judge a handful of historical runs under the new one. If the scores move, your baseline moved, and you'll know it was the judge, not the agents.
:::

## Manual corrections

Sometimes the eval is wrong, not the agent. A judge reads a rubric's parenthetical as a requirement; a matcher misses a legitimate paraphrase. When you can *demonstrate* a test result is wrong against the recorded evidence, correct it:

```bash
apo runs correct run_de89cab "report-is-complete" --pass \
  --reason "Retention is present in the KPI table; judge missed it"
```

Three terms keep this honest:

- The **recorded result** is what evaluation emitted, immutable, with its assertions, reasoning, and judge evidence.
- A **correction** is an append-only human decision (who, when, why) that sets one test's **effective** result to PASS/FAIL, or restores the recorded one.
- The **effective result** (latest active correction, else the recorded result) is what run verdicts, batch rollups, lists, stats, new comparisons, and `runs show --exit-status` all use.

A correction is not a re-judge: a re-judge produces a new *machine* judgment; a correction records a *human* one about existing evidence. Both leave the original verdict inspectable, `apo runs judgments` still lists the original machine counts verbatim.

Correcting history does not fix the future. After correcting, repair the test itself (a better instruction, a `similarity` matcher where wording varies) so the next run doesn't need the correction.
