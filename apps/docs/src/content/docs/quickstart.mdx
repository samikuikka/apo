**Zero to an executable definition of done.** Publish a Task, connect your machine, run the real agent from the dashboard or CLI, and read the pass/fail breakdown and evidence.

:::note[Two entry paths]
- **Invited to an existing hosted apo?** You don't need this page, go to [Hosted Alpha](/hosted-alpha/).
- **Running your own apo server?** Continue here.
:::

## 1. Bring up the stack

Self-host from source:

```bash
git clone https://github.com/samikuikka/apo.git
cd apo
scripts/self-host init --profile local
scripts/self-host up --build
```

Wait for readiness:

```bash
curl -fsS http://localhost:8000/health/ready | jq
# {"ok": true, ...}
```

Open `http://localhost:3000` and create the first admin account. Full details in [Self-Hosting](/self-hosting/topology/).

## 2. Authenticate

Install the CLI, then log in:

```bash
npm install -g @apo-ai/cli
```

## 3. Publish your Task catalog

Tasks live in your code, authored in TypeScript using the [`@apo-ai/sdk`](https://www.npmjs.com/package/@apo-ai/sdk) package. Install it in your application's repository first:

```bash
npm install @apo-ai/sdk
```

New to apo? The canonical example is a real Vercel AI SDK agent that extracts data from an invoice. See [`START-HERE.md`](https://github.com/samikuikka/apo/blob/main/apps/example-service/e2e/agent-task-demo/START-HERE.md) for the four-file map (real agent, adapter, task, inputs). Or just look at a live workspace first, any Apo install's [demo](/demo) is browsable without an account, pre-loaded with captured runs, checks, judges, and traces.

See [Define a Task](/guides/define-a-task/) for the authoring flow. Once defined, publish their metadata so the dashboard and `apo connect` can see them:

<TerminalDemo
  command="apo task publish --dir ./my-tasks"
  lines={[
    { parts: [{ text: "✓ Published 2 tasks to acme-eval", tone: "success" }] },
    { text: "  digest: sha256:a1b2c3d4..." },
    { text: "  published_at: 2026-07-31T12:00:00Z" },
  ]}
/>

This sends Task IDs, display names, adapter names, check flags, and each Task's canonical `*.eval.ts` definition, no fixtures, application source, credentials, or environment values.

## 5. Connect for dashboard runs

For persistent execution, so the dashboard and Schedules can dispatch work to your machine:

<TerminalDemo
  command="apo connect --dir ./my-tasks"
  lines={[
    { text: "Discovered 2 tasks in ./my-tasks" },
    { parts: [{ text: "Connected to a1b2c3d4 · catalog matches · capacity 4", tone: "success" }] },
    { text: "Waiting for assignments…  Ctrl+C to stop" },
  ]}
/>

Now any Run created from the dashboard Tasks page or a Schedule is claimed and executed on this machine. The Run's Trace, Tests, and Deliverables appear in the dashboard.

## 6. Run from the dashboard

Open `http://localhost:3000`, go to **Tasks**, select one or more Tasks, and click **Run**. The Run is queued, claimed by your connected machine, and executed locally.

The result is binary, pass or fail. Click any Run to see the full breakdown: which tests passed, which failed, and the trace showing every call the agent made.

## The workflow

```text
apo task publish     → publish your Task metadata (no source)
apo connect          → connect as a persistent executor
dashboard / schedule → queue work to your machine
                     → Tasks execute against your local source
                     → results, traces, and deliverables flow back
```

At no point does the server receive your source code, repository credentials, or environment variables. The Control Plane coordinates identity and metadata; your machine owns execution.
