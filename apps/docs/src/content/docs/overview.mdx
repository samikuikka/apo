**apo turns expert knowledge into a harness-engineering loop.** Your experts define what the agent system must be capable of—the real jobs, conditions, outcomes, and requirements that define done—and apo makes that standard executable.

<EndToEndLoopDemo />

Apo runs the real harness, verifies the actual outcome, and returns pass or fail backed by the test breakdown, trace, and deliverables. If evaluation cannot complete, apo surfaces an execution error instead of inventing a verdict.

That same result serves two jobs:

- **Know what the system can do.** The suite is an executable record of the capabilities your organization requires. Run it as models, features, and harnesses change to see whether the same standard still holds.
- **Engineer the harness.** A developer or coding agent reads the verdict and evidence, changes the prompts, tools, context, orchestration, models, or code, and starts another Task Run. Expert judgment defines where the loop must converge; the coding agent finds the path.

Apo owns one Task Run and its evidence. It does not edit the implementation or autonomously rerun a failure. That separation is why apo returns a control signal another human or machine can act on, not merely a score to monitor.

Apo is not another eval framework, and not an observability platform. Testing frameworks start from a test case and evaluator. Observability platforms start from an execution record. Apo starts from the specification: what this harness must be able to do. The individual pieces can be assembled elsewhere; apo makes the specification and the harness-engineering loop one coherent system. [Why apo](/why-apo/) lays out the full map.

## It runs in your system

apo doesn't host a copy of your agent or score a prompt in a sandbox. An [adapter](/concepts/adapters/) you write invokes your real orchestration and agent code, with whatever safe test environment and dependencies the task requires. The adapter loads the inputs, invokes your agent, and collects the structured deliverable the tests assert on.

You don't change your agent to fit apo. The adapter is a shim that calls your existing code (your chat function, your tool definitions, your model client) as-is. apo adapts to your system; your system doesn't adapt to apo.

This is the part that's yours to build, because it has to be. No framework can ship a generic adapter that meaningfully tests *your* agent against *your* application. apo gives you the lifecycle, the tracing, and the test runner; you give it the seam.

## It judges what the agent produced

apo judges the **task outcome**: the file written, the state changed, the action taken, the structured output returned, or the conversation the task required. A fluent self-report does not excuse a wrong result.

The deliverable is declared up front, collected by the adapter after the run, and schema-validated before the tests see it. You're asserting on what the agent actually *did*, not merely whether its account of the work sounded right.
