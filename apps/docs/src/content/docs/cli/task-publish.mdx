# apo task publish

Publish a Task catalog from your local workspace. The catalog tells the server which Tasks exist and includes each Task's canonical `*.eval.ts` definition source (so the dashboard can render the historical code behind stored check evidence). It does **not** upload fixtures, application source, repository credentials, prompts, or environment values.

## Synopsis

```bash
apo task publish [--dir <path>] [--project <id>] [--dry-run] [--strict-removal] [--allow-empty] [--json]
```

## Why publish

The dashboard's Tasks page, Schedules, and `apo connect` all need to know which Tasks exist in your workspace. `apo task publish` sends:

- Task IDs (hierarchical, e.g. `support/refund`)
- Display names
- Adapter names
- Whether each Task has checks
- Tags
- Each Task's `description` (from its `task()` options), shown on its dashboard card
- Git provenance, best-effort: for each Task, the author and date of the first commit that added its `.eval.ts`; plus the repo's HEAD commit, recorded on removal tombstones so a removal points into your history. Outside a git repo (or on a shallow clone) it is simply absent — the dashboard then falls back to the first user who published the Task.
- The canonical Task Definition, the normalized `*.eval.ts` text (capped at 1 MB), so the dashboard can show the exact source that produced stored evidence

No fixtures (`files/`), application source, repository credentials, or environment values are sent.

## Usage

```bash
# Publish from the current directory
apo task publish

# Publish from a specific Task root
apo task publish --dir ./my-tasks
```

Output:

```
✓ Published 14 tasks to acme-evals
  digest: sha256:a1b2c3d4...
  published_at: 2026-07-31T12:00:00Z
```

## Removal report

When a publish changes which Tasks exist, the command reports the diff after the success line — removals first, with their consequences:

```
✓ Published 43 tasks to acme-evals
  digest: sha256:9f3ab2e1...
  published_at: 2026-10-15T12:00:00Z

  removed    ai-sdk-agent/serving-integrity
             ⚠ 43 runs retained — findable under Status ▸ Archived
             ⚠ selected by schedule "nightly" — resolution will name the removal date
  added      harbor/terminal-bench/query-tcp-ports
  moved?     (root)/t-jev-split → (root)/t-jev-cascade (identical definition 7c1e55…)
```

The report is warning-only and the command still exits `0` — the catalog must converge with your repo either way, including in CI. `--strict-removal` is the one exception, below. Nothing is destroyed by a removal: every run, check, and trace is kept, and the removed Task stays findable in the dashboard under **Status → Archived** with its folders and run history (see [Tasks: removing a task](/concepts/tasks/)).

`moved?` appears when a removed and an added Task pin byte-identical definition content in the same publish — near-certainly a rename or move. History is never rewritten automatically; the report just tells you the split happened.

## The strict gate

`--strict-removal` turns costly removals into a non-zero exit. A removal is costly when it retains runs or when a schedule selected the Task. This is the CI tripwire:

```bash
apo task publish --dry-run --strict-removal
```

The dry-run form decides **before** anything is published, from a read-only catalog fetch. Its delta names the runs a removal would archive; schedule references are server-side knowledge, reported by the real publish. Bare `apo task publish --strict-removal` runs the gate after the publish converges your catalog with git — useful as an alarm, not as a blocker. Silent removals (no runs, no schedules) always pass, and an unreadable catalog never fails the gate.

## When to re-publish

Re-publish whenever you:

- Add a new Task
- Remove or rename a Task
- Change a Task's adapter or checks

`apo connect` detects catalog mismatches automatically and pauses until you re-publish. The connection resumes without restart.

## The catalog digest

The server computes a canonical SHA-256 digest over the normalized catalog (sorted by Task ID, canonical JSON). `apo connect` computes the same digest locally and sends it with each heartbeat and claim. If the digests differ, claiming is paused, this prevents executing a Task that has changed since publication.

## Flags

| Flag | Default | Description |
|------|---------|-------------|
| `--dir <path>` | `./e2e` (from config) | Task workspace root |
| `--project <id>` | Configured project | Override the target project. |
| `--dry-run` | off | Print what would change versus the current catalog, without publishing. Performs one read-only catalog fetch; `--json` stays a pure local print. |
| `--strict-removal` | off | Exit `1` when a removal would take runs or schedules with it. |
| `--allow-empty` | off | Allow publishing a catalog with zero discovered Tasks. |
| `--json` | off | Emit machine-readable JSON. |
